## Початок і завершення завдання

1. Прочитати цей файл і [стан проєкту](docs/PROJECT_STATUS.md).
2. Перевірити `git status`, останні commits, пов'язаний код, документацію та тести.
3. Відрізняти факти коду, результати поточних перевірок, історичні звіти та плани. Task 001 не вважати повністю підтвердженим без серверних перевірок.
4. Не перезаписувати чужі незакомічені зміни й не переписувати працюючі компоненти без потреби.
5. Після роботи оновити PROJECT_STATUS; за потреби ARCHITECTURE, DECISIONS і README. Запустити релевантні перевірки та чесно повідомити обмеження.

## Архітектура та незмінні обмеження

- Ціль: Central API на Fastify + PostgreSQL, frontend React + Vite, Node.js agents. Повна схема — [ARCHITECTURE](docs/ARCHITECTURE.md).
- Node.js 22 LTS; backend і agents запускаються через systemd. Поточний `engines` допускає `>=22`, але це не змінює цільову версію.
- На поточному етапі Docker заборонений для Node Control: не створювати Dockerfile/Compose, контейнерні залежності або контейнери. Існуючі сторонні контейнери не чіпати. Контейнеризація API/Agents — окрема фаза після MVP, тестів і стабілізації production, лише за новим завданням. PostgreSQL/Nginx залишаються на хості; їх перенесення не погоджено.
- API та Agent не запускати через PM2; він керує лише застосунками користувачів. Agent працює незалежно від PM2. Production frontend — статична React/Vite-збірка через host Nginx, без окремого Node.js-процесу.
- Новий backend/frontend/agent код — TypeScript зі строгими типами, валідацією зовнішніх даних, централізованим логуванням, обробкою помилок, graceful shutdown та environment-конфігурацією. Наявні JS-скрипти не переписувати без потреби. Node.js-сервіси не запускати від root без доведеної необхідності.
- PostgreSQL і Nginx працюють на хості. Окрема БД `node_control_db`, роль `node_control_user`, адреса `127.0.0.1:5432`; секрет DB_PASS лише в `.env` або існуючому менеджер секретів.
- Міграції — версійні SQL-файли `backend/migrations/` (node-pg-migrate, ADR-009): лише additive/forward, без production `down`; API їх не запускає.
- Не змінювати сторонні БД, ролі, сервіси або конфігурації. Зовнішній доступ до PostgreSQL не відкривати без окремого підтвердження.
- Nginx-конфігурації — `/etc/nginx/`; перед застосуванням змін обов'язковий `nginx -t`.
- Agents ініціюють вихідне захищене з'єднання до API; публічні вхідні порти на серверах agents не потрібні.
- Redeploy через API існуючого Jenkins і його pipelines. Секрети застосунків не дублювати в БД Node Control.

## Безпека

Agent: перевірка авторизації кожної команди, аудит керуючих дій, мінімальні права, явний дозвіл на керовані процеси. Ураховувати Linux-користувача та PM2_HOME; сторонні процеси не керувати без дозволу. Відкритий remote execution endpoint заборонений. Прикладний SQL — параметризований; пов'язані операції — транзакційні. Не розширювати HBA без необхідності; віддалений доступ потребує захисту й перевірки мережевих правил.

Мінімальні привілеї. Кожна адміністративна операція потребує авторизації та Audit Log. Agents не виконують довільні shell-команди: лише визначені й перевірені операції. Не виводити паролі, токени, приватні ключі або SCRAM-verifiers у логи чи відповіді. `.env` не комітити, права — `600`; у Git лише `.env.example`. Перед commit перевірити diff та `npm run check:secrets`. Сканер має обмеження; позитивний результат не є універсальною гарантією відсутності секретів.

## Тести та Git

- Новий код: Vitest для unit/integration за замовчуванням; відступ обґрунтувати. Чинний `node:test` залишити для існуючих скриптів. Frontend E2E може використовувати Playwright. Кожен endpoint: позитивні, негативні та authorization tests; адміністративна дія: дозволені й заборонені сценарії. Production-дані під час тестів не змінювати.
- Authentication, RBAC, Agent commands, process management, database access, deployment actions та Audit Logs — критичні компоненти з орієнтиром 100% покриття.

- Жодна реалізація не завершена без тестів: unit та integration; API, E2E, security і regression — відповідно до змінених сценаріїв. Нові та змінені гілки логіки покривати до 100%, де технічно доцільно, без формальних тестів заради coverage.
- Не видаляти тести заради успіху, не приховувати помилки й не пропускати перевірки без пояснення. При падінні встановити причину, виправити в межах завдання й повторити; проблему середовища явно зафіксувати.
- Команди та межі тестування — [DEVELOPMENT_RULES](docs/DEVELOPMENT_RULES.md). Наявні npm scripts: загальні — `npm test`, `npm run test:integration`, `npm run check:secrets`, `npm run check`, `npm run db:check`, `typecheck` і `lint` (backend, frontend, e2e, agent), `check:local`; backend — `backend:build`, `test:backend`, `test:backend:smoke`, `test:backend:db` (opt-in); agent — `agent:build`, `test:agent`, `test:agent:pm2` (opt-in); frontend — `frontend:build`, `test:frontend`; E2E — `test:e2e`, `test:e2e:pm2` (opt-in).
- Перед commit: diff, секрети, тести, `npm run typecheck` і `npm run lint` (охоплюють `backend/`, `frontend/`, `e2e/`, `agent/`; старі JS-скрипти перевіряє `node:test`). Formatter не налаштований — не повідомляти про його запуск.
- Після успішного завершення — commit і push у поточну робочу гілку; повідомити hash. Push лише за успішних перевірок і дозволених правил гілки. Не force-push, не змінювати історію без дозволу, не обходити захист гілки.
- Документаційний commit не означає готовності реалізації чи дозволу на деплой. За актуальним bootstrap-запитом документаційний push дозволений після успішних релевантних перевірок документів, unit-тестів і секретів, з чесним звітом про недоступні перевірки БД. Для функціональних змін і деплою потрібні всі релевантні успішні тести.

## Деплой та промпти

Кожне незалежне review Claude, незалежно від розміру завдання, виконувати за [AI_WORKFLOW — незалежний review](docs/AI_WORKFLOW.md#незалежний-review), включно з двобічною перевіркою документації та висновком APPROVED / CHANGES REQUIRED. До APPROVED попереднього завдання не створювати промпт на нову функціональність; промпти на виправлення дозволені.

Перед деплоєм перевірити конфігурацію, тести й залежності, підготувати rollback. Після — systemd status, health endpoint, логи, доступність і відсутність нових критичних помилок. Неперевірений код не деплоїти. Руйнівні операції потребують підтвердження. Наявний `db:setup` змінює сервер і не є read-only перевіркою.

Для промпту Claude спочатку вивчити код, попередні реалізації та залежності. Вивести самодостатнє технічне завдання одним суцільним Markdown code block із контекстом, метою, scope, обмеженнями, покроковою реалізацією, безпекою, тестами, acceptance criteria, deployment procedure, rollback, commit message, push instructions і форматом звіту. Деталі — [AI_WORKFLOW](docs/AI_WORKFLOW.md).

Фактичний процес і межі деплою — [DEPLOYMENT](docs/DEPLOYMENT.md). Для rollback застосунку передбачити backward-compatible міграції; відновлення виконувати лише якщо воно безпечне для даних.
