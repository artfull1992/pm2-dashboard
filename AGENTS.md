## Початок і завершення завдання

1. Прочитати цей файл і [стан проєкту](docs/PROJECT_STATUS.md).
2. Перевірити `git status`, останні commits, пов'язаний код, документацію та тести.
3. Відрізняти факти коду, результати поточних перевірок, історичні звіти та плани. Task 001 не вважати повністю підтвердженим без серверних перевірок.
4. Не перезаписувати чужі незакомічені зміни й не переписувати працюючі компоненти без потреби.
5. Після роботи оновити PROJECT_STATUS; за потреби ARCHITECTURE, DECISIONS і README. Запустити релевантні перевірки та чесно повідомити обмеження.

## Архітектура та незмінні обмеження

- Ціль: Central API на Fastify + PostgreSQL, frontend React + Vite, Node.js agents. Повна схема — [ARCHITECTURE](docs/ARCHITECTURE.md).
- Node.js 22 LTS; backend і agents запускаються через systemd. Поточний `engines` допускає `>=22`, але це не змінює цільову версію.
- Docker заборонений для Node Control: не створювати Dockerfile/Compose і не запускати компоненти в контейнерах. Існуючі сторонні контейнери не чіпати.
- PostgreSQL і Nginx працюють на хості. Окрема БД `node_control_db`, роль `node_control_user`, адреса `127.0.0.1:5432`; секрет DB_PASS лише в `.env` або існуючому менеджер секретів.
- Міграції мають бути версійними та відтворюваними; їх поки немає.
- Не змінювати сторонні БД, ролі, сервіси або конфігурації. Зовнішній доступ до PostgreSQL не відкривати без окремого підтвердження.
- Nginx-конфігурації — `/etc/nginx/`; перед застосуванням змін обов'язковий `nginx -t`.
- Agents ініціюють вихідне захищене з'єднання до API; публічні вхідні порти на серверах agents не потрібні.
- Redeploy через API існуючого Jenkins і його pipelines. Секрети застосунків не дублювати в БД Node Control.

## Безпека

Мінімальні привілеї. Кожна адміністративна операція потребує авторизації та Audit Log. Agents не виконують довільні shell-команди: лише визначені й перевірені операції. Не виводити паролі, токени, приватні ключі або SCRAM-verifiers у логи чи відповіді. `.env` не комітити, права — `600`; у Git лише `.env.example`. Перед commit перевірити diff та `npm run check:secrets`. Сканер має обмеження; позитивний результат не є універсальною гарантією відсутності секретів.

## Тести та Git

- Жодна реалізація не завершена без тестів: unit та integration; API, E2E, security і regression — відповідно до змінених сценаріїв. Нові та змінені гілки логіки покривати до 100%, де технічно доцільно, без формальних тестів заради coverage.
- Не видаляти тести заради успіху, не приховувати помилки й не пропускати перевірки без пояснення. При падінні встановити причину, виправити в межах завдання й повторити; проблему середовища явно зафіксувати.
- Команди та межі тестування — [DEVELOPMENT_RULES](docs/DEVELOPMENT_RULES.md). Наявні npm scripts: `npm test`, `npm run test:integration`, `npm run check:secrets`, `npm run check`, `npm run db:check`.
- Перед commit: diff, секрети, тести, доступні lint/format checks. Наразі lint/formatter не налаштовані — не повідомляти про їх успішний запуск.
- Після успішного завершення — commit і push у поточну робочу гілку; повідомити hash. Push лише за успішних перевірок і дозволених правил гілки. Не force-push, не змінювати історію без дозволу, не обходити захист гілки.
- Документаційний commit може чесно зафіксувати невдалі перевірки; він не означає готовності реалізації чи дозволу на деплой. Якщо повний check падає, push не виконувати, доки умову користувача про успішні перевірки не виконано.

## Деплой та промпти

Перед деплоєм перевірити конфігурацію, тести й залежності, підготувати rollback. Після — systemd status, health endpoint, логи, доступність і відсутність нових критичних помилок. Неперевірений код не деплоїти. Руйнівні операції потребують підтвердження. Наявний `db:setup` змінює сервер і не є read-only перевіркою.

Для промпту Claude спочатку вивчити код, попередні реалізації та залежності. Вивести одне цілісне копійоване технічне завдання з вимогами до тестів, деплою, rollback, commit/push і критеріями приймання; межі авторизації вказати явно. Деталі — [AI_WORKFLOW](docs/AI_WORKFLOW.md).
