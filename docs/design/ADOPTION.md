## Пріоритет та узгоджені рішення

За конфлікту: явні актуальні інструкції користувача → безпека й перевірені контракти → ТЗ разом із доповненням → PNG → старі концепти. Статус «для погодження» у незміненому початковому пакеті відображає його історію; поточний статус джерел визначає цей документ і запит користувача 2026-10-23.

- Зберегти scoped RBAC, broker target/identity checks, підтвердження команд і fail closed для логів після 401/403/404/409. Кеш на offline-макеті не дозволяє показувати текст після відмови доступу або створювати лог, якого не отримували.
- Підсумки «23», «20», «3», «2/2», порядок процесів і приклади історії — fixture, не контракт. Поточний Applications API не має глобальних totals; чинна keyset-пагінація й алфавітне сортування зберігаються. Не підганяти дані чи сортувати лише поточну сторінку під PNG.
- Тема пакета — темна. Наявна світла тема й системний вибір теми зберігаються; окремого світлого PNG-еталона тут немає.
- Touch-мінімум 44 px діє за прийнятою політикою `any-pointer:coarse` незалежно від desktop-ширини. Статичні кнопки 36–40 px не скасовують touch-вимог. Не копіювати відсутність фокуса/підтвердження зі статичного PNG.
- Stopped/errored і offline/stale — різні поняття. Відображення «—» для показників у списку й нейтральний поточний стан за відсутності свіжих даних — UI-проєкція, не зміна inventory/status у БД. Чинні правила команд і пороги не змінюються.
- APP-10 — можливість переглядати метрики без керування, а не дозвіл читати весь ресурс/логи. Viewer не отримує logs:read через наявність вкладки в макеті.
- Пакет дає точні еталони **Applications** і спільних компонентів. Для решти сторінок є лише текстовий §11 і загальні токени; їхні точні макети не надано.

## План зіставлення з поточним frontend

Етапи 1/2 до `2510092` отримали review за попереднім текстовим промптом. Це не ретроспективне підтвердження відповідності новому пакету: PNG тоді не були джерелом review. Подальшу візуальну відповідність перевіряти окремим follow-up перед розширенням редизайну на решту сторінок.

Перевірити в наступному frontend-завданні:

## Обов'язковий frontend-review

1. У промпті й звіті вказати версію джерел та відповідні ID екранів APP-01…APP-16 / DS-01.
2. Відтворити відповідні стани на синтетичних fixtures. Для порівняння PNG — той самий viewport, DPR 1, zoom 100%, стабільний час і вимкнені анімації. Порівнювати структуру, щільність, відступи, типографіку, компонування, видимі стани та контроли; не вимагати тотожного згладжування системного шрифту.
3. Надати screenshots реалізації та перелік усіх відхилень. Відхилення через API/безпеку пояснити конкретним контрактом; довільні дизайнерські відступи не вважати погодженими.
4. Окремо перевірити keyboard/focus, contrast, touch/fine, 390/1024/1366/1440 px і reflow/zoom. Responsive viewport сам по собі не є перевіркою справжнього browser zoom або touch.
5. Функціональними тестами підтвердити ізоляцію даних/прав, async race handling, cleanup polling, stale/offline, підтвердження команд і збереження scroll/фільтрів. PNG та `validation.json` цього не доводять.
6. Не запускати команди над production-процесами заради візуальної перевірки. Висновок review — APPROVED / CHANGES REQUIRED одночасно щодо коду, тестів, документації та застосовних дизайн-вимог.

`QA.md` і `validation.json` — звіти автора пакета, не незалежний прогін Codex. У поточному аналізі прочитано текст і вихідні макети, перевірено manifest і переглянуто всі стани на загальному аркуші та ключові PNG повнорозмірно; скрипти пакета не виконувались. Повторний render і функціональні тести продукту не заявляються.

## Результат етапу 2.1 — зіставлення реалізації з еталонами (2026-10-23, до review Codex)

Реалізацію узгоджено з APP-01…APP-16 і DS-01. Кожен стан відтворює `e2e/ui-tests/design-reference.spec.ts` на синтетичних fixtures як у макетах: 23 процеси на node-a / node-b, фіксований час 10:22:02 (Київ), темна тема, DPR 1, zoom 100 %, без анімацій. Матриця нижче — висновок Claude, а не незалежний висновок. Незалежне підтвердження дає лише review Codex.

**Спільні винятки** (застосовні до всіх desktop-кадрів):
- **E1 — підсумки.** Чипи «Усі 23 / Працюють / Зупинено / Невідомо / Агенти 2/2» не показано, і «Показано N із M» теж немає. Причина: API не дає глобальних scoped-підсумків. Замість них — «На цій сторінці: N» і свіжість («Усі дані актуальні · час» / «Є неактуальні дані: N»).
- **E2 — порядок.** Серверний: назва → сервер, keyset по 50. Порядок fixture в PNG — не контракт.
- **E3 — брендинг.** Не перенесено «GOIT · OPERATIONS», аватар «DA», «Demo Admin» і footer «Design 1.0 / Дані синтетичні». У профілі — справжні email і роль, «Обліковий запис», «Вийти».
- **E4 — одиниці.** «2.1 %» і «МіБ» — українська нотація, як на решті сторінок (у PNG — «2.1%», «MiB»).
- **E5 — шрифт.** Системний шрифт: згладжування й ширина гліфів відрізняються.

Результат zoom-перевірки — 11/11 (опис і обмеження — у PROJECT_STATUS). Ручне натискання Ctrl/Cmd + у видимому браузері не виконувалося.

## Етап 3.1 — Огляд, Сервери, деталі сервера (2026-10-23, до review Codex)

Точних PNG цих сторінок пакет не містить. Тому компонування спирається на ТЗ §11, DS-01 і вже реалізовані примітиви Applications; це не копія ненаданих макетів.

- **Огляд:** заголовок і свіжість, компактні підсумки, «Потребують уваги» (рядок застосунку: назва, стан, сервер), сервери, останні керуючі дії (лише для дозволених ролей).
- **Сервери:** щільна таблиця з полів list API — назва, стан агента, останній сигнал (вік і точний час), ключ.
- **Деталі сервера:** заголовок зі станом; контекст (сигнал агента, load average, агент); компактна таблиця процесів зі спільною проєкцією стану.

Перевірки — `e2e/ui-tests/stage31.spec.ts` і справжній browser zoom 200 % (`chrome.tabs.setZoom`). Сповіщення, аудит, користувачі, інтеграції, профіль і login — наступні підетапи.
