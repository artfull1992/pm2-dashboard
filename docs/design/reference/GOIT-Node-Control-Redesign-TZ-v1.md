# GOIT Node Control — технічне завдання на редизайн

Версія 1.0 · 22.10.2026 · адресат: Codex для рев’ю та підготовки промпту для Claude.

## 1. Розподіл відповідальності та статус

Автор дизайну готує макети та це ТЗ. Codex перевіряє відповідність фактичному репозиторію, знаходить суперечності, уточнює план і готує цілісний промпт для Claude. Claude відповідає за реалізацію, тести та подальший процес доставки згідно з правилами репозиторію й погодженнями користувача.

Користувач обрав напрям B: темна тема та постійна панель деталей праворуч. Уточнені макети й конкретні параметри цього документа — пропозиція для погодження; вибір напряму не є дозволом на деплой. Цей документ не є промптом для Claude. У межах підготовки дизайну код, конфігурація та керування сервісами не змінюються.

## 2. Мета та незмінні обмеження

Прискорити сценарій «знайти застосунок → оцінити стан і свіжість → відкрити логи → виконати дозволену дію». Зберегти існуючу роботу, маршрути, права, брокер команд, allowlist, маскування логів та аудит. Застосунок — головний об’єкт; сервер — контекст. Проблема спочатку, контекст потім, подробиці за запитом.

Це не розширення системного моніторингу: Zabbix залишається окремим інструментом. Без нових графіків, історії CPU/RAM, деплою, bulk-команд, AI, нової моделі прав або керування глобальним PM2. Не створювати та не видаляти PM2-процеси. Не мігрувати стек: systemd, PostgreSQL і Nginx на хості; Docker у межах редизайну не додається.

## 3. Джерело та межі аудиту

Проведено браузерний огляд адміністративного desktop-інтерфейсу 22.10.2026: Огляд, Сервери, деталі сервера, Застосунки, їх Огляд/Логи/Історія дій, Сповіщення, Користувачі, Журнал аудиту, інтеграції, правила, Обліковий запис. Перевірено пошук, поєднання фільтрів і порожній результат. Команди та запис налаштувань не виконувалися. Інші ролі, mobile, повний accessibility-аудит і командні підтвердження не перевірені. Висновки про їх поточну реалізацію робити не можна.

Макети — візуальні орієнтири, не джерело істини про дані та API. Назви, числа і логи на них синтетичні. Випадкові додані генератором елементи, значення, пояснення причин зупинки чи невідповідні лічильники не є вимогами. За конфлікту: обмеження користувача → перевірена поведінка/безпека → текстове ТЗ → зображення. Суперечність із фактичним контрактом необхідно явно винести в рев’ю.

## 4. Applications: компонування

Desktop від 1280 CSS px: ліва навігація 184–208 px, решта — робоча область. Заголовок, компактні підсумки та фільтри над двома панелями. Початкова пропорція списку й деталей 56/44, із перевіркою довгих назв і придатної ширини журналу. Не додавати drag-resize без окремої потреби.

Список і деталі прокручуються незалежно; їх заголовки й фільтри лишаються доступними. Сторінка не повинна мати два вкладені вертикальні скроли для одного журналу. Фокус клавіатури завжди видимий.

Підсумки — невеликі фільтри/лічильники, а не чотири великі картки. Значення будуються лише з доступних достовірних даних. Явно відрізняти загальну кількість доступних процесів від результату фільтра «Показано N із M». Не рахувати невідомі або застарілі процеси як підтверджено працюючі. Якщо API не дає глобального підсумку, не вигадувати його й не розширювати API мовчки.

Фільтри: пошук за назвою, сервер, статус. Зберегти поточні значення статусів. Пошук доступний за label, а не лише placeholder. Додати явне скидання всіх активних фільтрів. Не стирати фільтри через оновлення даних або вибір процесу.

## 5. Компактний список і вибір

Висота рядка 48–56 px; текст мінімум 14 px. Колонки: назва (сервер другим рядком), стан, CPU, RAM, короткий час роботи. Решта — у правій панелі. CPU та RAM вирівняти праворуч, використовувати табличні цифри. Назви не переносити посимвольно; повну назву робити доступною при обрізанні, також із клавіатури.

Один вибраний процес одночасно. Натискання назви/контролу вибору відкриває деталі без втрати позиції списку, пошуку та фільтрів. Виділення — синя межа й приглушений фон. Не використовувати лише колір для стану чи вибору. Не робити інтерактивний рядок із вкладеними конфліктними кнопками.

Ідентичність вибору не може бути лише PM2 id: він локальний і може змінюватися. Codex має перевірити наявний стабільний ключ та використовувати його разом із сервером відповідно до поточної моделі, без нової моделі ідентичності.

Пропозиція сортування: спочатку стани, що потребують уваги, далі алфавіт. Сам по собі stopped не називати аварією. Оновлення метрик не повинно постійно переставляти рядки під курсором; CPU/RAM не задають автоматичний порядок. Політику перестановки після зміни статусу Codex має узгодити з наявною поведінкою й описати у промпті. Вибраний об’єкт не перемикається автоматично на інший.

Якщо фільтр приховав вибраний об’єкт: зберегти його деталі та пояснити «Вибраний застосунок поза поточним фільтром». Якщо об’єкт зник із PM2: повідомити про це, заблокувати команди, не перевикористовувати деталі для іншого процесу з тим самим PM2 id. На першому вході без вибору показати «Оберіть застосунок, щоб переглянути деталі».

## 6. Права панель

Заголовок: повна назва, сервер, стан і актуальність. Компактний блок CPU/RAM/uptime. Вкладки «Огляд», «Логи», «Історія дій». Огляд містить PM2 id, режим, кількість рестартів із поясненням «усього», точний час збору та доступність керування. Не розмножувати однакові показники в кількох сусідніх блоках.

Перше відкриття — Огляд. При переході між застосунками зберігати активну вкладку, але завантажувати дані нового об’єкта з його дозволами. Старий запит не може підмінити дані нового вибору. Під час завантаження старий журнал не видається за журнал нового процесу. Зберегти наявні прямі посилання; новий спосіб кодування вибору в URL — лише після перевірки роутера. Не передавати в URL секрети або текст логів.

## 7. Логи

stdout/stderr, ручне оновлення, наявне автооновлення; частоту та ліміти брати з поточних контрактів. Не додавати справжній streaming, пошук по архіву або завантаження всього файла. Зберегти ліміти обсягу й маскування. Не виводити фрагменти логів у списку застосунків: журнал завантажується тільки за явного відкриття.

Показувати час отримання журналу окремо від часу зміни файла та збору PM2. Коротке повідомлення про останній фрагмент і кнопку подробиць; не обіцяти повного захисту від секретів. Для невідомих форматів зберегти попередження з чинної реалізації.

Автооновлення не скидає вибраний потік, текстове виділення й позицію при читанні старих рядків. Прокручувати донизу лише якщо користувач уже біля кінця. Перемикання процесу скасовує/ігнорує попередній запит; вихід із вкладки або сторінки очищає polling. При недоступності агента чітко позначити кешований результат або показати стан недоступності, якщо кешу немає. Не підміняти його порожнім «усе добре».

## 8. Стани та безпечне керування

| Ситуація | Відображення | Дії |
|---|---|---|
| Агент онлайн, збір актуальний, процес online | Зелений «Працює», поточні метрики | Лише дозволені чинним API команди |
| Актуальний stopped | Amber «Зупинено»; причину не вигадувати | Доступність start/restart/stop визначає чинний брокер і стан |
| Errored | Червоний «Помилка», відомий контекст | Лише дозволені команди, без автовиконання |
| Агент не звітує | Останній сигнал, попередження, «останній відомий стан» | Керування недоступне за політикою брокера; пояснення поруч |
| Агент онлайн, PM2 застарів | Окремий стан «Дані PM2 застарілі» | Не прирівнювати до online; перевірити чинну політику команд |
| Невідома метрика | «—», пояснення за потреби | Не перетворювати на 0 |
| Немає прав/allowlist | Причина недоступності | Не дозволяти обхід через інший екран |
| Запит не вдався | Зрозуміла помилка й повтор читання | Не оголошувати збій запиту падінням процесу |

Червоний — підтверджена помилка, amber — попередження/зупинка, сірий — невідомо, синій — вибір. Завжди текст плюс візуальний маркер. Пороги актуальності й offline не змінювати через дизайн.

«Перезапустити» — нейтральна контурна кнопка в деталях, інші команди — у меню; за відсутності дозволу показати пояснення за чинним UX-патерном. Не визначати дозволи лише з ролі на клієнті. Перед остаточною командою показувати ім’я, сервер, дію та наслідок відповідно до існуючого механізму підтвердження. Зберегти блокування дублювання, стан очікування, результат і аудит. Відправлена команда не означає, що процес уже працює. Не створювати новий командний протокол.

## 9. Адаптивність і доступність

1024–1279 px: компактна навігація, список на всю ширину, деталі окремою панеллю/екраном. До 1024 px: послідовний сценарій список → деталі → назад; повернення зберігає фільтри та позицію. На 390 CSS px — без горизонтального скролу всієї сторінки; горизонтальний скрол допустимий усередині журналу. На 200% zoom елементи не перекриваються.

Tab/Shift+Tab, Enter/Space для вибору, коректні tablist/tab/tabpanel, aria-selected, доступні назви іконок. Меню та modal повертають фокус до виклику; Escape закриває overlay без команди. Якщо бічна панель modal на mobile — focus trap; немодальна desktop-панель не блокує фокус списку. Контраст основного тексту ≥4.5:1, великих написів та потрібних меж/контролів ≥3:1. Перевірити контраст реально, кольори нижче — стартові токени. Не дублювати live-оголошення кожної метрики на кожному polling.

## 11. Застосування до інших сторінок

Єдині токени й компоненти поширити на всі сторінки, включно з login, без зміни їх логіки. Огляд — компактні підсумки й прямий контекст застосунку; порожні блоки «0 проблем» не займають половину екрана. Сервери — стан агента та вік даних, не системні графіки. Деталі сервера використовують спільні компоненти станів і рядків процесів. Інциденти — окремо причина відкриття, поточне значення, причина закриття. Користувачі — стислий рядок і роль, UUID у подробицях. Аудит — зрозумілі назви подій і користувачі, ID доступні без втрати. Інтеграції — стан доставки першим, деталізація черги згорнута. Правила — одиниці біля полів, групування й чинна валідація збережені. Профіль — та сама форма й чинна політика сесій.

Не збільшувати scope API під виглядом оформлення. Якщо ім’я автора або показник на момент відкриття інциденту відсутні в даних, показати чесний fallback і винести окрему залежність.

## 12. Окремі знахідки, не змішувати з візуальним рефакторингом

Перевірити неузгоджений порядок дат у журналі: 13–14 жовтня перед 22 жовтня попри заявлений reverse chronology. Перевірити показ «+0 рестартів» у закритому інциденті «Часті рестарти». Це спостереження, не встановлені причини дефектів. Codex має відтворити на контрольованих даних і виділити окремі виправлення з тестами, якщо дефекти підтвердяться. Не змінювати історичні дані та семантику подій для відповідності макету.

## 13. Критерії приймання та перевірки

- На 1440×900 і 1366×768 закриті деталі не впливають на висоту рядків; у списку видно щонайменше 9 повних рядків без прокручування всієї сторінки. Перевірити 23 і 100+ синтетичних процесів, довгі назви, кілька серверів та однакові локальні PM2 id.
- Вибір між двома процесами на вкладці логів не змішує відповіді, метрики або права; фільтри й scroll зберігаються. Вибраний зниклий процес не замінюється мовчки.
- Відкриття/оновлення списку не запитує логи кожного процесу. Вихід припиняє polling. Ліміти й маскування лишаються чинними.
- Stopped не позначається автоматично «аварія». Offline/stale не демонструє останні значення як живі й не дозволяє заборонених команд. «—» відрізняється від 0.
- Оператор із частковими правами, спостерігач і адміністратор отримують свої чинні можливості; UI не замінює серверну перевірку. Зберегти тести ізоляції доступу.
- Команда має ідентифікований об’єкт і підтвердження, не дублюється подвійним натисканням; timeout і відмова не видаються за успіх. Перевіряти через mocks/тестовий агент, не production.
- Порожні результати, loading, помилки мережі, старі дані, відсутній кеш логів, процес поза фільтром мають явні стани.
- Перевірити keyboard, focus, contrast, 390/1024/1366/1440 px та zoom 200%; надати screenshots із синтетичними даними для нормального, stopped і offline станів.
- Запустити чинні lint/typecheck/unit/integration/e2e перевірки за правилами репозиторію; додати змістовні сценарії для нової взаємодії та регресій. Не писати snapshot-тести лише на значення кольорів.
- Без успішних обов’язкових тестів деплой не допускається. Обсяг і момент деплою визначаються окремим погодженим процесом, не цим ТЗ.

## 14. Що має зробити Codex перед промптом для Claude

1. Прочитати AGENTS.md та поточні документи/історію роботи у репозиторії. Перевірити router, UI-компоненти, API, freshness, broker capabilities, log polling, дозволи й поточні тести. Не починати переписування з нуля.
2. Зіставити кожну вимогу з існуючою реалізацією; відділити оформлення, взаємодію, підтверджені дефекти й можливі backend-залежності. Не припускати endpoint або структуру таблиць.
3. Підготувати рев’ю ТЗ: неоднозначності, ризики, розбіжності з кодом, потрібні погодження. Рутинні значення в межах вимог вирішувати без зайвих зупинок.
4. Сформувати один цілісний промпт для Claude з фінальним scope, заборонами, конкретними перевірками та критеріями завершення. Урахувати попередні коміти, не втрачати вже реалізоване.
5. Рекомендований порядок реалізації для подальшого погодження: спільні токени та компоненти → Applications split-view і стани → перенесення системи на інші сторінки → окремі підтверджені виправлення аудиту/інцидентів.

Результат цього етапу: дизайн та ТЗ для рев’ю Codex. Це не задача на негайну реалізацію чи деплой Claude.
