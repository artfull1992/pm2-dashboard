# GOIT Node Control · Design reference 1.0

23.10.2026. Напрям B: темна тема, компактний список і постійні деталі праворуч.

Статус: точний дизайн-пакет для погодження та рев’ю. Це не реалізація продукту, не підключений до API прототип і не дозвіл на деплой. Користувач погодив напрям; нові деталі пакета потребують візуального перегляду. Автор дизайну → Codex (рев’ю вимог, промпт) → Claude (реалізація).

## Додати до репозиторію

Скопіювати всю папку `docs/design/` з архіву в корінь репозиторію. Не замінювати однойменні існуючі документи без порівняння. Не включати код макетів у production bundle. У пакеті немає секретів, реальних логів або даних користувачів.

- `screens/` — контрольні PNG, 1 CSS px = 1 px зображення.
- `source/index.html`, `style.css`, `mockups.js` — точні вихідні макети. Статичні контролі навмисно не виконують дії.
- `source/render.cjs` — відтворення знімків і перевірка overflow/помилок JS.
- `reference/GOIT-Node-Control-Redesign-TZ-v1.md` — незмінений знімок початкового ТЗ.
- `SPEC-ADDENDUM.md` — уточнення до ТЗ, які роблять макети однозначними.
- `validation.json` — результат локальних перевірок рендерингу, не тестів продукту.

Відкрити `source/index.html?view=logs` через локальний HTTP-сервер або file URL. Інші view наведені нижче. Для file URL додати query в адресі браузера вручну. Макети не є клікабельним застосунком; окремі URL представляють окремі зафіксовані стани.

## Як робити рев’ю реалізації

1. Codex звіряє ТЗ, це доповнення і фактичні контракти репозиторію. Потім готує промпт Claude. Не вигадувати API, права або стабільний ключ процесу.
2. Для кожного стану відтворити синтетичний fixture або його семантичний аналог у тестовому середовищі. Скриншотити той самий viewport при zoom 100%, DPR 1, з вимкненими анімаціями й стабільним часом.
3. Порівнювати структуру, рядки 48–56 px, видимі стани, відступи, розміщення контролів, контраст і збереження контексту. Системний шрифт може трохи змінювати растеризацію: це не причина міняти логіку продукту.
4. Функціональні правила перевіряти тестами: відсутність змішування запитів, cleanup polling, stale/offline, підтвердження команд, серверні дозволи, повернення focus/scroll. PNG цього не доводить.
5. Команди перевіряти лише на тестових даних/агенті. Жодних restart/stop у production заради візуального рев’ю.
6. Показники та імена у fixture — не очікувані production-значення. Не підганяти API або історичні дані під приклад.

Пріоритет: вимоги користувача й чинна безпека → перевірені контракти → ТЗ з доповненням → ці PNG → старі imagegen-концепти. Не реалізовувати випадкові деталі старих згенерованих зображень.

## Відтворення PNG

Потрібні Node.js, Playwright та Chromium. Використати затверджені залежності репозиторію; не міняти його версії заради дизайну. З папки `source/`: `node render.cjs`. Якщо використовується власний Chromium, передати абсолютний шлях через `DESIGN_CHROMIUM_PATH`. Установлення браузера — стандартний механізм обраної версії Playwright. Жодних мережевих ресурсів у самих макетах немає.

Макети підтримують viewport 390–1440 px. Автоматичні зміни вибору/фільтрів, drag-resize, реальні меню та команди не реалізовані — вони описані в ТЗ для продукту. Навігаційні піктограми — локальні текстові позначки для геометрії; в реалізації використати існуючий набір іконок.

## Межі пакета

Це детальні еталони Applications та спільної дизайн-системи. Інші сторінки мають успадкувати токени за §11 ТЗ, але окремі точні макети цих сторінок у цей пакет не входять. Не вважати їх візуально погодженими. Повна перевірка accessibility, ролей і API можлива лише в реалізованому продукті.
