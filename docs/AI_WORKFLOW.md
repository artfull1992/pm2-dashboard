# Взаємодія користувача, Claude та Codex

Claude — основний виконавець. Codex — незалежний reviewer, архітектор та альтернативний виконавець за запитом користувача. Робочий інтерфейс — VS Code; не вимагати переходу в інший інтерфейс, якщо роботу можна виконати тут. Усі відповіді та документи — українською.

## Постійний контекст

На початку кожного завдання прочитати [AGENTS.md](../AGENTS.md), [PROJECT_STATUS](PROJECT_STATUS.md), перевірити status, останні commits, пов'язані файли та тести. Для архітектурних змін прочитати ARCHITECTURE і DECISIONS; для виконання — DEVELOPMENT_RULES. Не покладатися лише на пам'ять чату або попередній AI-звіт.

Після роботи оновити стан, за потреби архітектуру, рішення й README; провести релевантні перевірки, commit/push згідно із завданням. Документи мають відображати фактичний код. Секрети не переносити в контекст, промпти чи звіти.

## Промпт для Claude

Спочатку вивчити код, попередні реалізації, тести та залежності. Вивести весь самодостатній промпт одним суцільним Markdown code block для копіювання одним натисканням; не розбивати на кілька блоків і не додавати сторонніх пояснень усередину. Обов'язкові дані:

1. Контекст, мета, поточний підтверджений стан, залежності та конкретні файли.
2. Scope, архітектурні обмеження, вимоги до поведінки, безпеки та сумісності.
3. Покрокова реалізація; тести: unit/integration та відповідні API/E2E/security/regression, негативні сценарії й команди перевірок.
4. Деплой: чи входить у scope, передумови, конфігурація, rollback і перевірки після застосування. Не надавати необмежений дозвіл на production-зміни.
5. Оновлення документації, diff/secrets review, commit message, push у дозволену поточну гілку після успішних перевірок.
6. Критерії приймання та формат звіту з реальними результатами, hash і проблемами.

Якщо деплой не потрібний, прямо вказати це у вимогах. Не приховувати невідомі параметри за вигаданими рішеннями.

## Незалежний review

Зіставити завдання з diff і кодом, перевірити реальні тести, побічні ефекти, секрети, авторизацію, аудит і rollback. Відрізняти дефект від непідтвердженого стану середовища; для висновку дати шлях/код або результат перевірки. Серверні аудити зберігати поза публічним репозиторієм; нову перевірку позначати окремою датою та доказами.

Фінальний звіт: стан репозиторію; висновки Task 001; створені й оновлені файли; зафіксовані правила; результати тестів; branch/hash; push status; проблеми; наступний крок. Не заявляти про дії, що не виконувались.

Review охоплює Git diff, відповідність архітектурі, security, error handling, зміст/покриття тестів, regression risks, міграції, deployment safety та documentation consistency. Зауваження: пріоритет, шлях/рядок, конкретний ризик і потрібна перевірка. Не погоджуватися автоматично зі звітом Claude. Промпт на виправлення — за запитом, одним code block.

Deployment procedure формувати з [DEPLOYMENT](DEPLOYMENT.md), не вигадувати units/шляхи. Вказувати конкретний commit message, push instructions, acceptance criteria й rollback. Якщо деплой не потрібен, зазначити, що він не входить у scope, та визначити rollback самих змін.
