# Взаємодія користувача, Claude та Codex

Claude — основний виконавець. Codex — незалежний reviewer, архітектор та альтернативний виконавець за запитом користувача. Робочий інтерфейс — VS Code; не вимагати переходу в інший інтерфейс, якщо роботу можна виконати тут. Усі відповіді та документи — українською.

## Постійний контекст

На початку кожного завдання прочитати [AGENTS.md](../AGENTS.md), [PROJECT_STATUS](PROJECT_STATUS.md), перевірити status, останні commits, пов'язані файли та тести. Для архітектурних змін прочитати ARCHITECTURE і DECISIONS; для виконання — DEVELOPMENT_RULES. Не покладатися лише на пам'ять чату або попередній AI-звіт.

Після роботи оновити стан, за потреби архітектуру, рішення й README; провести релевантні перевірки, commit/push згідно із завданням. Документи мають відображати фактичний код. Секрети не переносити в контекст, промпти чи звіти.

## Промпт для Claude

Спочатку вивчити код, попередні реалізації, тести та залежності. Вивести весь самодостатній промпт одним суцільним Markdown code block для копіювання одним натисканням; не розбивати на кілька блоків і не додавати сторонніх пояснень усередину. Обов'язкові дані:

1. Контекст, мета, поточний підтверджений стан, залежності та конкретні файли.
2. Scope, архітектурні обмеження, вимоги до поведінки, безпеки та сумісності.
3. Покрокова реалізація; тести: unit/integration та відповідні API/E2E/security/regression, негативні сценарії й команди перевірок.
4. Деплой: чи входить у scope, передумови, конфігурація, rollback і перевірки після застосування. Не надавати необмежений дозвіл на production-зміни.
5. Оновлення документації, diff/secrets review, commit message, push у дозволену поточну гілку після успішних перевірок.
6. Критерії приймання та формат звіту з реальними результатами, hash і проблемами.

Якщо деплой не потрібний, прямо вказати це у вимогах. Не приховувати невідомі параметри за вигаданими рішеннями.

## Незалежний review

Для frontend-завдань обов'язкові [ТЗ та дизайн-еталони](design/ADOPTION.md), погоджені користувачем 2026-10-23: у промпті та review вказувати застосовні APP/DS ID, порівнювати screenshots реалізації й документувати відхилення. Макети не замінюють перевірок поведінки, авторизації й API; пріоритет і межі визначено в ADOPTION.

Ці правила застосовуються до кожного review реалізації Claude незалежно від розміру завдання й доповнюють AGENTS.md без зміни розподілу відповідальності. Зіставити погоджений промпт із diff і кодом; перевірити коректність логіки, регресії, архітектуру, безпеку, error handling, авторизацію, аудит, міграції, rollback, наявність і фактичні результати потрібних тестів та відсутність зайвих змін поза scope. Відрізняти дефект від непідтвердженого стану середовища; не погоджуватися автоматично зі звітом Claude. Серверні аудити зберігати поза публічним репозиторієм; нову перевірку позначати окремою датою та доказами.

Документацію перевіряти обов'язково у двох напрямках:

- **Code → Docs:** зміни поведінки, налаштувань, експлуатації та відновлення мають бути відображені в потрібних документах.
- **Docs → Code:** чинні інструкції та описи мають відповідати реалізації й не суперечити один одному. Перевіряти архітектуру й взаємодію компонентів, API, конфігурації та env, встановлення, оновлення, rollback, права й безпеку, діагностику, логи та відновлення після збоїв. Історичний звіт не підміняє актуальну інструкцію.

Документація має дозволяти адміністратору експлуатувати Node Control як self-hosted продукт без читання вихідного коду. Оновлювати лише документи, для яких є реальна потреба; не переписувати історичні факти як поточний стан.

Фінальний звіт: стан репозиторію; висновки Task 001; створені й оновлені файли; зафіксовані правила; результати тестів; branch/hash; push status; проблеми; наступний крок. Не заявляти про дії, що не виконувались.

Кожен висновок має явний статус:

- **APPROVED** — реалізація, потрібні тести й документація відповідають вимогам у зазначених межах перевірки.
- **CHANGES REQUIRED** — знайдено помилки, регресії, порушення правил чи невідповідності документації. Кожне зауваження містить пріоритет, конкретне місце, проблему/наслідок та очікуваний результат виправлення й перевірки.

Неперевірені речі не позначати успішними. Необхідні, але недоступні перевірки й інші обмеження явно зазначати; без необхідного підтвердження готовності не видавати APPROVED.

За CHANGES REQUIRED Claude виправляє зауваження, Codex повторює review; цикл триває до APPROVED. До APPROVED попереднього завдання новий промпт на реалізацію наступної функціональності не створюється. Баги, регресії та документація мають пріоритет; промпт на виправлення — за запитом, одним code block. Якщо нові правила отримано під час review, продовжити його з урахуванням цих правил і не змінювати незавершену реалізацію Claude.

Deployment procedure формувати з [DEPLOYMENT](DEPLOYMENT.md), не вигадувати units/шляхи. Вказувати конкретний commit message, push instructions, acceptance criteria й rollback. Якщо деплой не потрібен, зазначити, що він не входить у scope, та визначити rollback самих змін.
