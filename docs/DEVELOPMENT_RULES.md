# Правила розробки, перевірок і деплою

Основні обмеження — [AGENTS.md](../AGENTS.md); стан перевірок — [PROJECT_STATUS](PROJECT_STATUS.md). Працювати малими змінами в межах завдання, не ламати існуючі компоненти й сторонню інфраструктуру.

## Перевірки

Новий backend/frontend/agent код — TypeScript зі строгими типами, валідацією зовнішніх даних, централізованими логами без секретів, обробкою помилок і graceful shutdown. Зберігати conventions, аналізувати залежності, не дублювати функції; чинні JS-скрипти не мігрувати без потреби. Сервіси не запускати від root без доведеної необхідності.

Прикладний SQL — параметризований, пов'язані операції — транзакційні. Наявні setup SQL builders обмежують identifiers/екранують literals; це не заміна параметризованих запитів API. Agent: авторизація кожної команди, Audit Log керуючих дій, мінімальні права та явні дозволи на процеси з урахуванням Linux-користувача/PM2_HOME. Remote execution endpoint заборонений.

Agent/machine routes (Task 007): machine-маршрути декларують `config.access: { machine: 'agent' }`; тести — розділення browser/machine credentials, підміна ідентичності, ліміти, malformed payload; real-DB — конкурентність (ротація, heartbeat, revoke). Agent — лише Node built-ins, без `rejectUnauthorized:false`, без HTTP поза loopback dev-режимом.

Frontend (Task 006): нові екрани — компонентні тести (стани loading/empty/error/forbidden/unavailable), без HTML з API, без web storage для сесійних даних; auth-сценарії — Playwright E2E лише проти тестової БД. Dev-backend для UI — `NODE_ENV=development`, `AUTH_COOKIE_SECURE=false` лише на loopback, `AUTH_ALLOWED_ORIGINS=http://127.0.0.1:5173`.

Auth/RBAC (Task 005): кожен новий `/api`-маршрут декларує `config.access`; тести — позитивні, 401, 403 (матриця ролей) і для state-changing — Origin/CSRF; API-тести використовують `FakeAuthStore` (атомарна семантика), SQL-семантика — `backend/test/db/auth.test.ts` у тестовій БД. Request-схеми лише з явними `properties` і `additionalProperties: false` (NC-SEC-001 відкрито).

Для нового коду використовувати Vitest для unit/integration, якщо відступ не обґрунтований. Існуючий node:test зберегти: чинні скрипти вже покриті ним. Frontend E2E може використовувати Playwright. Endpoint: позитивні, негативні та authorization tests; адміністративна дія: дозволені й заборонені сценарії. Критичні компоненти (authentication, RBAC, Agent commands, process management, DB access, deploy, Audit Logs) мають орієнтир 100% покриття.

Обов'язкова цільова перевірка — Node.js 22 LTS. Старий `tests/integration` (node:test, `.env`, production `node_control_db`) з Task 004 **лише read-only**: перевірки прав #9/#10 виконуються через каталоги PostgreSQL, без CREATE/INSERT/DROP. Тести із записом — тільки `backend/test/db/*` проти `node_control_test_db` у власній схемі `nc_test_<ms>_<hex8>`; cleanup видаляє лише цю схему, ніколи БД. Привілейований suite потребує root на хості PostgreSQL (`runuser`, `psql`, systemd); локально пропускається з поясненням. Успіх локально не замінює серверну перевірку.

Production-дані під час тестування не змінювати. Тести із записом — лише в ізольованій `node_control_test_db` (Task 004); `tests/integration` проти production — read-only. Read-only аудит і тести із записом розділяти.

Для реалізації потрібні unit та integration tests; для API — API tests, користувацьких сценаріїв — E2E, прав доступу — security, багів — regression. Перевіряти реальні результати та негативні сценарії, не копіювати код у фіктивні assertions. Ціль — 100% нового/зміненого коду, де доцільно. Документаційні зміни перевіряти на узгодженість із кодом і працездатність локальних посилань; вони не потребують вигаданих API/E2E тестів.

При падінні тестів визначити причину. Не видаляти перевірки, не позначати недоступну БД як успіх, не називати build успішним при падінні тестів. Виправлення поза поточним обсягом оформити окремою задачею. Lint і typecheck налаштовані для `backend/`; formatter відсутній — перевіряти `git diff --check`, не заявляти про запуск неіснуючих інструментів.

## Git та review

Перед змінами — status і history; перед commit — повний diff, секрети, релевантні тести та доступні статичні перевірки. Додавати лише власні зміни явними шляхами. Не комітити `.env`, tokens, ключі, DB dumps або credential-bearing logs. Сканер не перевіряє всю історію самостійно й має обмеження розміру/шаблонів; за підозри перевіряти історію без виводу значень.

Commit має описувати фактичну зміну. Push — у поточну дозволену робочу гілку після успіху перевірок; захист `main` не обходити, force push заборонений. Документаційний commit із зафіксованими невдалими integration checks не підтверджує готовність коду. У звіті зазначити branch, hash, результати й фактичний push status.

## Деплой

1. Звірити scope, версію коду, конфігурацію без секретів, залежності та тести. Визначити користувача сервісу, шляхи й rollback до змін.
2. Підготувати backup тільки потрібних конфігурацій/даних і контрольований спосіб відновлення. Не відкривати PostgreSQL ззовні, не змінювати сторонні сервіси.
3. Виконати лише погоджені зміни. Nginx: конфігурація в `/etc/nginx/`, перед застосуванням `nginx -t`. Backend/agents: systemd, мінімальні права. `db:setup` — мутація з root, не перевірка стану.
4. Перевірити systemd status, health endpoint (коли буде реалізовано), логи, доступність, сторонні сервіси й критичні помилки. При невдачі — rollback за планом і повторна перевірка.

Деплой — лише versioned-артефактом (`scripts/deploy/build-release.js` → `server-release.js`, DEPLOYMENT). Історичний rsync у `/etc/pm2-dashboard` не використовується. Конфіг сервісу — `/etc/node-control/api.env` (`600 nodecontrol`).

Перед commit запускати `npm run typecheck` і `npm run lint` (backend, frontend, e2e, agent); для старих JS-скриптів lint не налаштований. За актуальним bootstrap-запитом документаційний push дозволений після успішних релевантних перевірок документів, unit-тестів і секретів із чесним зазначенням недоступності БД. Це не дозвіл на деплой із failing tests.

Фактичний workflow та backward-compatible rollback міграцій — [DEPLOYMENT](DEPLOYMENT.md).

### PM2 inventory (Task 008)

- **Жодних `pm2`-команд поза тимчасовим `PM2_HOME`**, навіть `pm2 --version`: без `PM2_HOME` CLI запускає daemon у `~/.pm2` поточного користувача.
- Код exporter не імпортує `pm2` і `child_process` і викликає лише `getMonitorData` (це перевіряє тест). Нові PM2-методи — лише окремим рішенням (ADR).
- Сирий `pm2_env` не серіалізується, не логується і не передається далі: тільки allowlist-поля; тести — із синтетичними секретами в усіх полях `pm2_env`.
- Відсутні метрики — `null`, не 0; `unavailable` ≠ порожній список.
- JSON schemas на `/api` строгі (Ajv `removeAdditional: false`): нові клієнти не можуть надсилати недокументовані поля.

### Керування PM2 (Task 009)

- Нові PM2-методи — лише через тип `Pm2Method` у `agent/src/pm2/rpc.ts` і окреме рішення (ADR). Створення/видалення/reload/signal/stdin — заборонені.
- Broker: жодних shell/exec/eval, лише типізовані запити; результати — з enum причин, без тексту PM2.
- Тести керування на справжньому PM2 — лише одноразовий `PM2_HOME` (`npm run test:agent:pm2`, `npm run test:e2e:pm2`); `NC_BROKER_ALLOW_SELF_OWNED_ALLOWLIST` і `NC_AGENT_INVENTORY_ALLOW_SAME_OWNER` — лише в тестах.
- `test:e2e:pm2` запускається окремим прогоном: разом з іншими специфікаціями адміністратор перевищив би ліміт входів на акаунт (5 за 15 хв), який для тестів не послаблюється.
- UI ніколи не повторює мутацію автоматично й не показує «успішно» до підтвердженого статусу команди.

### Логи (Task 010)

- Текст логів не логувати, не писати в БД/audit, не класти в storage/URL; у тестах — синтетичні маркери й перевірка їх відсутності в журналах і audit.
- Broker читає лише шляхи з PM2 metadata у дозволених каталогах (`NC_BROKER_LOG_DIRS`); жодних шляхів/offset/glob від клієнта.
- Long-poll у Fastify: відключення клієнта слухати на `reply.raw` ('close'), не на `request.raw` (там 'close' спрацьовує після читання тіла). Регресійний тест — через справжній HTTP (`app.listen`), не `inject`.
- Timeout відповіді ≠ завершення операції: ресурсний слот (конкурентність, лічильник) звільняти лише у `finally` самої операції, рівно один раз; на осиротілий Promise — `.catch(() => undefined)`. Regression-тест — завислий mock, повторні timeout, пізні resolve/reject.
- Кожен waiter/таймер у пам'яті API має ліміт (на запит, на актора, глобальний), відмову до створення ресурсу й ідемпотентне завершення для result/deadline/timeout/disconnect/shutdown; перевіряти через `stats()` і `process.getActiveResourcesInfo()`.
- На macOS тимчасові каталоги — symlink (`/var` → `/private/var`): для тестів читання логів використовувати `realpathSync`.

### Користувачі та credentials (Task 011)

- Будь-яка зміна пароля, ролі чи активності користувача: у тій самій транзакції `credential_version + 1`, відкликання **всіх** його сесій і audit. Створення сесії перевіряє версію під `FOR SHARE`.
- Дорогий scrypt — лише поза транзакцією й через спільний bounded limiter; commit — compare-and-set на прочитаній версії. Row lock під час hashing не тримати.
- Адмінські мутації `users` — під `LOCK TABLE users IN SHARE ROW EXCLUSIVE MODE`, із повторною перевіркою актора (сесія + активний admin) під блокуванням. Порядок блокувань: таблиця `users` → рядки `users` → `sessions`.
- Гонки перевіряти real-DB тестами з утриманням блокування в окремому з'єднанні (`BEGIN … COMMIT`), а не лише через `Promise.all`.
- Паролі й hash не потрапляють у відповіді, audit, журнали, client storage чи URL; тести перевіряють відсутність синтетичних паролів у логах, audit і тілах відповідей.
- E2E: для сценаріїв з багатьма входами — окремий admin у per-run схемі (ліміт входів 5/15 хв на обліковий запис).
- Frontend: кожна асинхронна мутація прив'язана до сесії (`bindSession()` з `AuthContext`) і власного `AbortController`. Після **кожного** `await`, перед будь-яким побічним ефектом (стан, callback, reload, `passwordChanged`, `sessionExpired`) — перевірка `aborted || !binding.current()`. `apiRequest` не повертає результат, що надійшов після abort/timeout. Regression-тести — з transport, який завершується **після** abort (deferred), бо справжній `fetch` це приховує.
- Списки з keyset-курсором у UI — сторінками (`Назад`/`Далі`), ресурс keyed за курсором: дані іншої сторінки не показуються, запізніла відповідь відкидається. Неможливість дійти до записів після першої сторінки — дефект.

### Dashboard (Task 012)

- Підсумки — лише агрегатами backend по всіх записах (`count(*) FILTER`), не з першої сторінки списків і не запитом на кожен сервер. Списки обмежені й мають точний `total`. Агрегати та списки — в одній транзакції `REPEATABLE READ READ ONLY` від одного `now()`.
- «Поточний» стан процесу — лише активний online-сервер із `current` inventory. Метрики офлайн-сервера не показуються як поточні. Невідоме значення — `—`/`null`, не 0. Load average — не відсоток CPU.
- Поля, видимі не всім ролям (останні дії), фільтруються на backend і зовсім не запитуються для ролей без доступу.
- Nullable-об'єкти в response-схемах — через `type: ['object', 'null']`, не `anyOf`: тоді серіалізатор відкидає невідомі ключі, а не падає з 500.
- Read-only GET нічого не прострочує й не очищає: lifecycle команд лишається в чинних шляхах.

### Alerts і фонові worker (Task 013)

- Правила — чиста функція без I/O й годинника; час і вибірки — з БД. Кожну умову тестувати на відкриття, відновлення, гістерезис, повторний snapshot і відсутність даних.
- Стан, що має пережити restart (інциденти, cooldown, черга), — лише в БД; переходи й черга — одна транзакція; паралельність — advisory lock / `FOR UPDATE SKIP LOCKED` + lease, результат пише лише власник захоплення.
- Зовнішні HTTP-виклики: allowlist host/path, `redirect: 'error'`, тайм-аут + AbortSignal, обмежене читання відповіді, жодних URL чи тексту відповіді в журналах/помилках; тести — лише mock transport.
- Shutdown: ресурси, що тримають HTTP-запити (long-poll, waiters, worker), звільняти в `preClose`, а не в `onClose`; під час закриття відповіді з `Connection: close`. Regression — справжній HTTP + `lifecycle.shutdown()`.

### Налаштування й секрети в UI (Task 013.1)

- Прикладні параметри — в БД з `revision`/`generation` і optimistic concurrency (409 замість мовчазного перезапису); env — лише deployment-рівень (ключі, origin).
- Секрети, введені в UI: write-only, AES-256-GCM з випадковим nonce й AAD, ключ поза БД; відсутній або неправильний ключ → fail-closed без fallback на plaintext; секрет не повертається жодним GET і не потрапляє в audit/журнали; frontend-парсер відкидає відповідь, схожу на секрет.
- Hot reload: worker перечитує знімок налаштувань щоциклу; новий `AbortController` на кожен `start()`; зміна адресата скасовує стару чергу (не пересилає).
- Ручні зовнішні дії (тестове повідомлення) — без DB-транзакції під час мережі, один у польоті, без автоповтору, результат прив'язаний до generation.

## Frontend design: спокійна інфраструктурна консоль

Мета — один продукт на всіх сторінках: сутність або проблема → метрика → metadata. Нормальний стан тихий, проблеми помітні. Без gradients, glassmorphism, декоративних ілюстрацій, анімацій заради анімацій і сторонніх UI-бібліотек. Відсутню функціональність не імітувати.

**Tokens** (`frontend/src/styles.css`, `:root` і `prefers-color-scheme: dark`; редизайн B від 2026-10-22; інших кольорів/розмірів у правилах не вводити):
- тема — за налаштуванням ОС (`prefers-color-scheme`): темна й світла рівноправні, примусової теми немає;
- поверхні `--nav` (навігація, мобільний topbar), `--bg`, `--surface`, `--surface-2` (заголовки таблиць, hover), `--elevated` (вікна, меню); текст `--text`, `--text-muted`; межі `--border` (розділювачі), `--border-strong` (декоративні: пунктир порожніх станів, теги), `--control-border` (межі inputs, selects, кнопок — контраст ≥ 3:1); фокус `--focus`;
- акцент `--primary` (+ `--primary-soft` для активного пункту меню); стани `--success`/`--success-soft`, `--warning`/`--warning-soft`, `--danger`/`--danger-soft`; логи `--log-bg`/`--log-text`;
- контраст: текст ≥ 4.5:1 на кожній поверхні, межі контролів і фокус ≥ 3:1 — це перевіряє `e2e/ui-tests/foundation.spec.ts` за обчисленими токенами в браузері;
- відступи `--space-1…6` (4, 8, 12, 16, 24, 32 px); радіуси `--radius` (8 px: картка, таблиця) і `--radius-sm` (6 px: контроли); тіні мінімальні (лише вікна й меню), без градієнтів;
- типографіка: системний sans з кирилицею; основний текст `--text-md` 14/20 px (body, таблиці, контроли), `--font-sm` 13 px (другорядний), `--font-xs` 12 px (metadata — дрібніше не робити), `--text-lg` 16 px (заголовки секцій), `--text-xl` 18 px (заголовки вікон, значення метрик), H1 `--text-h1` 26/32 px; `--font-mono` для логів та ID; числа — tabular numerals; rem лишається 16 px (ширини в rem незмінні);
- висота контролів — два токени: `--control-h` (кнопки, inputs, selects, пункти навігації й меню, вкладки, affix-поля) і `--control-sm` (кнопки в рядках таблиць, pager, «Дії», мінімальна зона `.icon-button` по ширині й висоті). Розмір залежить від **способу вводу**, а не лише від ширини (`@media (max-width: 760px), (any-pointer: coarse)`):
  - **fine** — широке вікно, лише точні вказівники (миша, тачпад): 36 / 32 px, `.icon-button` ≥ 32×32;
  - **coarse** — є хоча б один грубий вказівник (телефон, touch-планшет будь-якої ширини): 44 / 44 px, `.icon-button` ≥ 44×44;
  - **hybrid** — і миша, і touch (ноутбук із сенсорним екраном): `any-pointer: coarse` істинне, тож діють 44 px навіть під час роботи мишею — палець завжди дістає контрол;
  - **narrow** — вікно ≤ 760 px навіть із точним вказівником: 44 px (одноколонкове компонування, ймовірний touch);
  - checkbox/radio завжди 16×16, зона натискання — їхня мітка `.check` (≥ 32 px). Breakpoint навігації (760 px) — це компонування, від способу вводу не залежить. Інших висот немає — це перевіряють `design.spec.ts`, `foundation.spec.ts` (touch-планшет 1024×768 з `hasTouch`, fine desktop 1440, вузьке вікно 390) і `settings-layout.spec.ts`;
- навігація 196 px (вимога 184–208 px від 1280 CSS px); активний пункт — тонований фон, акцентний текст і смуга зліва (не лише колір); фокус — 2 px `--focus` з відступом 2 px.

**Каркас сторінки.** `PageHeader` (`components/ui.tsx`): один `<h1>`, коротка ситуація/timestamp у `meta`, одна основна дія праворуч, breadcrumbs лише для вкладених сторінок (сервер). Блоки — `Section` (`<section aria-labelledby>` із `<h2>`). Рівно один рівень картки (`.panel`/`.card`): усередині картки — лише розділювачі (`border-top`), без вкладених рамок. Пояснення — коротко біля метрики, довше — у `<details class="disclosure">`; не покладатися лише на `title`/hover.

**Навігація.** Групи «Моніторинг» і «Адміністрування»; пункти й порожні групи без дозволу не показуються (API перевіряє права незалежно). Обліковий запис і вихід — у блоці профілю внизу sidebar. Topbar лише на мобільних і має функцію (кнопка «Меню»); закрите меню — `display:none` (немає прихованих focusable), Escape закриває й повертає фокус.

**Таблиці.** Назва сутності — `th scope="row"`, головний акцент; службові дані (PM2 id, exec mode, ID запитів) — `.secondary`/`.cell-meta`. Числа — `.num` (праворуч, tabular numerals), дати — `.date`; невідоме — «—», ніколи не 0. Спільний час збору — над таблицею, якщо він однаковий для всіх рядків; інакше — у кожному рядку. Дані офлайн-сервера або застарілі — `table--outdated`/попередження, не як live. Примітки до таблиці — `.table-note`. На мобільних таблиця прокручується горизонтально всередині `.table-wrap`, сторінка — ні.

**Робоча область «Застосунки»** (ADR-029). ≥ 1280 px — список і деталі поруч у висоті вікна (кожен прокручується сам; лог — єдина прокрутка панелі деталей). < 1280 px — окремі види з «Назад до списку» (фільтри, сторінка, прокрутка й фокус зберігаються). Рядок — одна кнопка 48–56 px без вкладених контролів; вибраний — фон + смуга + маркер + `aria-current`. Вибір не в URL; ідентичність `key + serverId + source + name`; поза рядками — перевірка через `GET /api/servers/:id/applications`, без підміни. Непідтверджений процес — лише з попередженням і заблокованими командами; відсутній чи відкликаний — без даних і логів. Не додавати: загальні підсумки, яких немає в API; сортування «спершу проблеми» в межах сторінки; polling на рядок; повні лог-файли; bulk-дії. Перевіряє `e2e/ui-tests/applications-detail.spec.ts` (≥ 9 повних рядків на 1440×900 і 1366×768, 23 і 120 процесів, 390/720/1024/1279/1280 px, touch, контраст, клавіатура).

**Статуси** — лише `StatusIndicator` (крапка + текст; колір не єдиний носій): `ok` — тихий (звичайний текст, зелена крапка), `muted` — нейтральний/невідомий, `warn` і `bad` — кольоровий текст на м'якому фоні. Не робити нормальні значення яскравими «пігулками».

**Форми й дії.** Одна primary-дія на рівні контексту; небезпечні — `button--danger` + підтвердження. Створення — кнопка в `PageHeader` і `FormDialog` (`components/Dialog.tsx`): форма підписана заголовком вікна; під час запиту вікно не закривається (Escape/«Скасувати» неактивні); закриття з введеними даними спершу питає (поля тоді приховані й `inert`, форма не надсилається — ні Enter, ні `requestSubmit`; «Повернутися до форми» повертає дані й фокус на поле, яке редагувалось; `[hidden]` завжди переважає `display` компонентів); невідомий результат (немає відповіді) прямо називається невідомим і перечитує список; відповідь після unmount/зміни сесії ігнорується (`bindSession` + `AbortController`); автоматичних повторів немає.

**Вікна** (`Dialog`): рендеряться в `<body>` через portal, `#root` отримує `inert` (фон неінтерактивний), фокус — на перший елемент у порядку документа, Tab циклічний усередині, фокус повертається на елемент, що відкрив вікно. Відкриття/закриття нічого не надсилає. Меню рядка («Дії», `ActionMenu`, ADR-024) — overlay через portal у `<body>` (`position: fixed`), не в потоці таблиці: не змінює геометрію рядка/таблиці й не обрізається `overflow`; семантика menu button (`role="menu"/"menuitem"`, стрілки, Home/End, Escape, Tab). Ключі рядків стабільні: polling не закриває меню й не губить фокус. Геометрію перевіряє `e2e/ui-tests/row-menus.spec.ts`.

**Перевірки дизайну:** `npx playwright test -c e2e/ui.config.ts` (синтетичний API; 1440/1366/1024/720 (zoom 200 %)/390 px, light/dark; контраст токенів, без горизонтального скролу, дві висоти контролів, клавіатура й фокус, жодних мутацій). Ця команда не входить у `check:local` — запускати її при кожній зміні frontend. Скріншоти — лише з `NC_UI_SHOTS=<каталог поза репозиторієм>` і лише синтетичні дані.
